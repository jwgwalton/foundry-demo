# Wella Foundry Demo --- Stub APIs and Tooling Specification

## Scope

This specification defines synthetic services for a fictional
professional hair-care organisation. They are intended solely to
demonstrate enterprise agent integration patterns relevant to a Wella
environment; they do not represent Wella's actual internal systems, data
models or architecture.

## Design goals

The services should:

-   be deterministic and easy to seed
-   expose realistic business capabilities
-   support automated tests
-   produce clean OpenAPI/MCP schemas
-   include deliberate negative/error fixtures
-   exercise multiple authentication patterns
-   run locally through Docker Compose
-   migrate cleanly to Azure-hosted equivalents
-   avoid real customer or commercially sensitive data

## Shared identifiers

Use stable synthetic identifiers.

``` text
Products:     PRODUCT-1042
Salons:       SAL-001
Orders:       ORD-10001
Cases:        CASE-20001
Warehouses:   WH-GB-01
```

Use ISO-style market codes such as `GB`, `DE`, `FR`.

## Service 1 --- Product Catalogue API

### Purpose

Represents an internal Product Information Management/catalogue
capability.

### Protocol

HTTP REST with OpenAPI 3.x generated by FastAPI.

### Authentication progression

Iteration 1: anonymous.

Iteration 2 onward:

``` http
X-API-Key: <key>
```

OpenAPI security scheme:

``` yaml
components:
  securitySchemes:
    ProductApiKey:
      type: apiKey
      in: header
      name: X-API-Key
```

### Operations

#### Get product

``` http
GET /products/{sku}
```

Suggested `operationId`:

``` text
get_product
```

Response:

``` json
{
  "sku": "PRODUCT-1042",
  "name": "Professional Permanent Colour 8/1",
  "category": "hair_colour",
  "product_line": "Professional Colour",
  "size_ml": 60,
  "status": "active",
  "markets": ["GB", "DE", "FR"]
}
```

Errors:

-   `401` invalid/missing credential when auth is enabled
-   `404` unknown SKU
-   `422` invalid path/input

#### Search products

Add after the basic lookup is stable.

``` http
GET /products/search?query={query}&category={category}
```

`operationId`:

``` text
search_products
```

Response should contain a bounded list with SKU, name, category and
status.

### Synthetic fixtures

Include:

-   active hair-colour product
-   active care product
-   discontinued product
-   similarly named products
-   product unavailable in GB
-   known SKU with no technical document

## Service 2 --- Inventory API

### Purpose

Represents ERP/supply-chain inventory data.

### Authentication

Use bearer-token authentication to exercise a different connection
pattern.

``` http
Authorization: Bearer <token>
```

For local development, deterministic token validation is sufficient. A
later Azure iteration can replace this with a production-like identity
mechanism.

### Operations

#### Get market inventory

``` http
GET /inventory/{sku}?market=GB
```

`operationId`:

``` text
get_inventory
```

Response:

``` json
{
  "sku": "PRODUCT-1042",
  "market": "GB",
  "available_units": 38,
  "reserved_units": 4,
  "status": "in_stock",
  "as_of": "2026-09-21T12:00:00Z"
}
```

The timestamp should be deterministic in tests.

Errors:

-   `400` unsupported market
-   `401` invalid token
-   `404` unknown SKU
-   `503` deterministic simulated upstream outage

#### Inventory by warehouse

Optional later operation:

``` http
GET /inventory/{sku}/locations?market=GB
```

`operationId`:

``` text
get_inventory_locations
```

Response:

``` json
{
  "sku": "PRODUCT-1042",
  "market": "GB",
  "locations": [
    {
      "warehouse_id": "WH-GB-01",
      "available_units": 24
    },
    {
      "warehouse_id": "WH-GB-02",
      "available_units": 14
    }
  ]
}
```

## Service 3 --- Salon CRM MCP Server

### Purpose

Represents a CRM/customer-service system for professional salon
accounts.

### Protocol

MCP.

### Authentication progression

Local development may begin without auth or with a deterministic
bearer/API token. The hosted version should be suitable for testing a
Foundry MCP connection and stronger Azure identity patterns.

### Tool: `search_salons`

Input:

``` json
{
  "name": "Bella Hair Studio",
  "city": "Brighton"
}
```

Output:

``` json
{
  "matches": [
    {
      "salon_id": "SAL-001",
      "name": "Bella Hair Studio",
      "city": "Brighton",
      "market": "GB",
      "status": "active"
    }
  ]
}
```

Include ambiguity in fixtures:

-   Bella Hair Studio --- Brighton
-   Bella Hair & Beauty --- London
-   Bella Studio --- Bristol

### Tool: `get_salon`

Input:

``` json
{
  "salon_id": "SAL-001"
}
```

Output:

``` json
{
  "salon_id": "SAL-001",
  "name": "Bella Hair Studio",
  "city": "Brighton",
  "market": "GB",
  "status": "active",
  "account_tier": "professional"
}
```

### Tool: `get_salon_orders`

Add later.

Input:

``` json
{
  "salon_id": "SAL-001",
  "limit": 10
}
```

Return deterministic synthetic order history.

### Tool: `create_support_case`

State-changing operation.

Input:

``` json
{
  "salon_id": "SAL-001",
  "category": "product_enquiry",
  "summary": "Salon requested availability and technical guidance for PRODUCT-1042."
}
```

Output:

``` json
{
  "case_id": "CASE-20001",
  "status": "created",
  "salon_id": "SAL-001"
}
```

Requirements:

-   validate salon existence
-   support idempotency to prevent duplicate cases on retry
-   expose created records to tests
-   reject malformed categories
-   deterministic IDs in test mode

### Tool: `reserve_inventory`

Add only after read/write behaviour is stable.

Input:

``` json
{
  "salon_id": "SAL-001",
  "sku": "PRODUCT-1042",
  "market": "GB",
  "quantity": 24,
  "idempotency_key": "..."
}
```

This is a consequential operation and should be called only after the
application has satisfied its approval policy.

Return:

``` json
{
  "reservation_id": "RES-30001",
  "status": "reserved",
  "quantity": 24
}
```

Reject:

-   insufficient stock
-   inactive salon
-   inactive product
-   unsupported market
-   duplicate action without matching idempotency semantics

## Service 4 --- Blob/Azurite Knowledge Store

### Purpose

Represents internal product, safety and education documentation.

### Local implementation

Use Azurite through Docker Compose.

Suggested container:

``` text
product-knowledge
```

Suggested blob hierarchy:

``` text
product-guidance/
├── PRODUCT-1042-technical-guide.md
├── PRODUCT-1042-safety-guide.md
├── PRODUCT-2091-technical-guide.md
├── colour-consultation-guide.md
└── colour-correction-guide.md
```

### Document metadata

Each seeded document should have metadata sufficient for deterministic
filtering.

Example:

``` json
{
  "document_id": "DOC-1042-TECH",
  "document_type": "technical_guide",
  "sku": "PRODUCT-1042",
  "market": "GB",
  "version": "1.0",
  "status": "active"
}
```

### Synthetic content

Technical documents should contain small, explicit facts that can be
evaluated, for example a synthetic mixing ratio, processing time,
compatible product family and warnings.

Do not use real Wella technical instructions unless intentionally
sourced and licensed for that purpose. Dummy guidance should be clearly
synthetic.

### Negative fixtures

Include:

-   SKU with multiple documents
-   SKU with no document
-   obsolete document
-   document for wrong market
-   similarly named document
-   conflicting obsolete/current versions

## Error simulation

Failures must be deterministic rather than random.

Recommended mechanisms:

``` text
/test/errors/401
/test/errors/429
/test/errors/500
/test/errors/503
```

or known fixture IDs that trigger specific behaviour.

This allows stable regression evaluations.


All services should expose health/readiness endpoints where applicable.

## Contract requirements

### OpenAPI

Every callable operation must have:

-   stable `operationId`
-   concise description
-   typed inputs
-   typed responses
-   documented error responses
-   authentication scheme where applicable
-   no ambiguous optional parameters unless intentional

Tool descriptions should explain *when* the operation is appropriate,
not merely repeat its name.

### MCP

Every tool should have:

-   stable tool name
-   concise capability description
-   strict input schema
-   structured output
-   explicit error response
-   deterministic test behaviour

### Security

Secrets must never be:

-   committed to Git
-   placed in prompts
-   returned from tools
-   logged in plaintext
-   included in traces

Use environment variables locally and Foundry/Azure connection or
identity mechanisms in hosted environments.

## Test requirements

Each service should have tests for:

-   happy path
-   schema validation
-   unknown resource
-   authentication failure
-   deterministic upstream failure
-   response contract

State-changing operations additionally require:

-   idempotency
-   duplicate request handling
-   authorization/approval boundary at application level
-   no mutation on invalid input

## Local-to-Azure mapping

``` text
FastAPI Product API  → Azure-hosted API
FastAPI Inventory    → Azure-hosted API
Local MCP            → Remote Azure-hosted MCP
Azurite              → Azure Blob Storage
Environment secrets  → Foundry connections / Azure identity
```

The service contracts should remain stable while infrastructure changes.
